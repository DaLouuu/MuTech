# Front end guide

Audience: whoever builds the user interface (front end owner). You do not need to know how the model works. You need the API contract, how to turn Hz into note names and cents, and the limits of the data.

## 1. What the user should be able to do

1. Choose or drop an audio file (WAV is the tested format).
2. Wait while it is analysed (about 0.7 seconds of waiting per second of audio on a small server, so a 3 minute song is over 2 minutes).
3. See every sung pitch over time as a pitch trace, with the note name and how many cents sharp or flat each pitch is.
4. Adjust a **sensitivity** control (the API's `threshold`) and re-view.

## 2. The API in one screen

Full reference: [BACKEND_GUIDE.md section 4](BACKEND_GUIDE.md#4-api-reference).

```
POST {BASE}/transcribe?threshold=0.5&hop=1      multipart form, field "file"
→ { sample_rate, hop_s, threshold, n_frames, process_s,
    frames: [ { t: seconds, f0: [Hz, Hz, ...] }, ... ] }
```

```js
async function transcribe(file, threshold = 0.5) {
  const body = new FormData();
  body.append("file", file);
  const res = await fetch(`${BASE}/transcribe?threshold=${threshold}&hop=1`, { method: "POST", body });
  if (!res.ok) throw new Error(`API error ${res.status}`);
  return res.json();
}
```

Things to design around:

- **It is slow.** There is no progress information from the API today. Show an indeterminate spinner and the file duration. Do not set a short fetch timeout.
- **One request at a time.** The server currently handles one analysis at a time. Disable the upload button while a request is running.
- **Browser calls need CORS.** The back end allows all origins by default. Tell the back end owner the exact address your front end is served from so it can be locked down.
- **Errors.** `415` wrong file type, `413` file over 30 MB, `422` bad setting.

## 3. Turning Hz into notes and cents

The API returns frequencies. The "note name and cents" display is your job. Equal temperament with A4 = 440 Hz:

```ts
const NAMES = ["C","C#","D","D#","E","F","F#","G","G#","A","A#","B"];

function hzToNote(hz: number, a4 = 440) {
  const midi = 69 + 12 * Math.log2(hz / a4);   // fractional MIDI number
  const nearest = Math.round(midi);
  return {
    name: NAMES[((nearest % 12) + 12) % 12] + (Math.floor(nearest / 12) - 1),
    cents: Math.round(100 * (midi - nearest)),  // negative = flat, positive = sharp
    midi,                                       // fractional, handy as the y coordinate
  };
}
```

Example: 196.0 Hz gives G3, 0 cents. 200 Hz gives G3, +35 cents.

The group's MuTech dashboard already has a canvas renderer, a frequency to screen mapping and a frequency to note and cents function in TypeScript. Reuse those if the group agrees rather than writing new ones.

## 4. Drawing the pitch trace

Plot **time on x, fractional MIDI number (or log frequency) on y**. A log axis is essential: equal musical intervals must look equal.

- Draw each `f0` value in each frame as a dot, or join dots between neighbouring frames when they are within about 1 semitone to get lines.
- Expect noise: single frame dots that appear and vanish. Dots that last fewer than about 3 frames (35 ms) are usually not real notes, so a minimum duration filter makes the picture much cleaner. This is a front end choice and needs no API change.
- Typical SATB range if you want a default y axis: roughly E2 (82 Hz) to A5 (880 Hz). The model's full range is C1 (32.7 Hz) to about 2,093 Hz.
- 30 seconds of audio is 2,583 frames and about 100 KB of JSON, so plain Canvas handles it fine. Use `hop=2` to `4` for long files if the drawing gets slow.

## 5. What the data can and cannot tell you (important for labels and tooltips)

| The data | Consequence for the UI |
|---|---|
| Pitches per frame are an **unordered set** | You cannot label lines "Soprano" or "Bass". Do not imply voices. Colour by register or leave one colour |
| The model's pitch grid is **20 cents wide** | Cents values are trustworthy to about ±10 cents. Do not display cents with false precision, and avoid colouring "in tune / out of tune" at tight limits such as ±5 cents |
| Noise in the recording makes the model **miss** pitches, not invent them | Gaps in the trace on a noisy recording are likely the model's, not the singers'. A note such as "Low volume or noisy sections may show gaps" is honest |
| With only 2 or 3 singers the model adds **extra pitches** | A sparse recording may show spurious dots, often an octave from the real note |
| Sensitivity (`threshold`) 0.5 to 0.7 is the useful range | A slider from 0.3 to 0.8 with 0.5 as default is reasonable. Higher = cleaner but may drop quiet notes |

## 6. Suggested first milestone

1. Hard code a saved API response (for example the sample in [BACKEND_GUIDE.md](BACKEND_GUIDE.md#4-api-reference), or one generated by the back end owner) and draw the trace from it. This lets you build the whole display without waiting for a server.
2. Add the note and cents tooltip using `hzToNote`.
3. Add upload and the sensitivity slider against a running back end.
4. Add the minimum duration filter and a legend that states the limits in section 5.

To get a real sample response without the server, ask the back end owner to run `curl -F "file=@x.wav" .../transcribe > sample.json` on any clip.
